# v51 — 把 /api/* 的两种实现收敛成一份，统一走 apiCore

> 发布日期：2026-11-23
> 基线：`e90e555`（v50-fix 之后）
> 起因：用户指出"能不能把后端和 mock 的处理逻辑统一起来，用同一份代码更好"

## 问题：同一套接口有两份实现，迟早漂移

v50 之前的状态：

| 位置 | 实现 |
| --- | --- |
| `server/server.ts` | 4 个 Express 路由，各自 `res.json(...)` |
| `src/core/mockApi.ts` | 同样 4 个接口的浏览器内等价逻辑 |

两份代码**看起来一样、实际不一样**，而且已经在悄悄分叉：

| 差异点 | 服务端 | 浏览器 |
| --- | --- | --- |
| 保存密钥错误提示 | 「保存密钥（Save Key）错误或缺失…」 | 「保存密钥错误（演示密钥：atlas-demo-key）…」 |
| 未配置密钥 | 403 | 回退到内置 `atlas-demo-key` |
| 限流 | 有（带定期清理） | 无 |
| 3xx 拦截 | 有 | 有 |
| SSRF 内网 IP 拦截 | 有 | 无（浏览器拿不到对端 IP） |
| 响应字段 | `{ok,status,responseBody}` | `{ok,status,responseBody,mock:true}` |

这类分叉不会立刻炸，但会在某天变成"本地能存、上线存不上"的玄学 bug。**收敛成一份**是唯一的长期解。

## 改动

### 新增 `src/core/apiCore.ts` —— 唯一实现

纯函数，不碰 HTTP、不碰 Express、不碰浏览器 fetch：

```
输入 ApiRequest  { method, path, headers, body: Uint8Array, clientId }
输出 ApiResult   { status, headers, body: Uint8Array }
```

`handleApiRequest(deps, req)` 是唯一入口，内部分发四个接口。有状态的依赖通过 `ApiDeps` 注入：

| 接口 | 服务端实现 | 浏览器实现 |
| --- | --- | --- |
| `BlueprintStore` | `createMemoryStore()` | IndexedDB |
| `RateLimiter` | 复用现有 `checkProxyRateLimit`（带清理） | `createWindowRateLimiter()` |
| `HttpFetcher` | 带 SSRF 防护（`validateProxyTargetUrl` + `dns.lookup` + `isPrivateOrReservedIP` + `sanitizeProxyHeaders` + 密钥注入） | 裸 `fetch`（浏览器做不到内网拦截，如实不做） |
| `mode` | `'server'` | `'browser'` |

**代理校验链**现在是唯一的一份，顺序刻意安排（便宜的先做）：

1. 限流 → 2. 方法白名单 → 3. URL 形状 → 4. 域名白名单 → 5. 头/体 → 6. 出站（10s 超时）→ 7. 拦截 3xx → 8. 响应限长 256KB

### `server/server.ts` 只剩传输适配

原来的 4 个路由（约 180 行业务逻辑）替换为：

- `toApiRequest(req)`：Express req → `ApiRequest`
- `writeApiResult(res, result)`：`ApiResult` → Express res
- 一个 `for` 循环挂 4 条路径

不重写任何业务逻辑，只做翻译。`/api/proxy/binary`、`/api/pdf/*` 保持不变（它们不是这四个契约接口）。

**部署层鉴权留在服务端**：`X-Proxy-Token` 校验不进 apiCore —— 浏览器没有可信的令牌存放位置（bundle 里的常量谁都能读），这层只在一侧成立，硬塞进共享层反而是假的对称。

### `src/core/mockApi.ts` 只剩浏览器适配

删掉全部重复的 `route()` 与 `handleProxy()`（约 130 行），改为：

- 装 fetch 拦截器
- 提供 IndexedDB 版 `BlueprintStore`
- 提供浏览器版 `HttpFetcher`
- 调 `handleApiRequest(browserDeps, ...)`

### 新增 `src/core/rpcClient.ts` —— WS 上的请求/响应配对

配置 `VITE_BACKEND_WS_URL` 时，`/api/*` 整包经 WS 送到服务端：

```
请求 { t:'rpc_req', id, method, path, headers, body, bodyEncoding }
响应 { t:'rpc_res', id, status, headers, body, bodyEncoding }
```

- `id` 配对，支持多请求并发在途
- 断线后所有在途请求立刻 reject（不让调用方干等超时）
- 指数退避重连，上限 15s
- 二进制按 base64 走，PDF 上传下载字节级一致

### 新增 `src/core/runtimeConfig.ts` —— 模式判定唯一入口

```
VITE_BACKEND_WS_URL 未配置 → 纯静态：浏览器内跑 apiCore
VITE_BACKEND_WS_URL 已配置 → 连后端：WS 转发，服务端跑同一份 apiCore
```

刻意不给 `localhost` 默认值：GitHub Pages 上任何写死的 localhost 都指向"访问者自己的电脑"，必然连不上。空着、让 UI 明示"当前是演示模式"，比一个看着能用实际永远失败的默认值好。开发态例外——同一个进程带着房间服务，回落到 `ws://localhost:8787/ws`。

## 服务端 RPC 为什么走自回环 HTTP

`makeRpcHandler(port)` 收到 `rpc_req` 后，对本机 `127.0.0.1:port` 发一次真实 HTTP 请求。

不用构造合成 `req/res` 对象的原因：Express 的整条中间件链（json/raw parser、限流、鉴权、`req.ip` 解析、静态资源）都依赖真实的 `IncomingMessage`/`ServerResponse`。伪造对象要么漏掉某层防护、要么在某些中间件里直接炸。回环多一跳本机 TCP，但拿到的是**和浏览器直连完全一致**的行为——这正是"复用"要的效果。

同时限制只允许 `/api/*` 路径，避免 WS 变成任意站点代理跳板。

## 顺手修掉的问题

- **`/api/room/stats` 被 SPA fallback 吃掉**（v50 遗留）：路由注册在 `app.listen` 之后，被 `app.get('*')` 先截走。移到 `/api/*` 同段，用模块级 `roomServer` 变量间接引用。
- **`.env.example` 的 `PORT` 写 3000** 而代码默认 8787：照抄的人服务起在 3000、前端连 8787，协同永远连不上。已改。
- **`App.tsx` 硬编码 `ws://localhost:8787/ws`**：改为读 `defaultRoomWsUrl()`。
- **协同弹窗文案还提到已删除的 `room-go`**：已更新，并在未配置后端时显示"纯静态演示模式"提示。
- **`serverRevision` / `serverBaseBlueprint` 两处模块级状态**（apiCore 的 store 接管后成为死代码）：已删。

## 已知遗留

- **浏览器模式仍无 SSRF 防护**：这是浏览器能力的硬限制，不是实现疏漏。要真防护必须配 `VITE_BACKEND_WS_URL` 走服务端。
- **WS 上跑 HTTP 语义是自己造的协议**：没有 HTTP/2 多路复用、没有标准状态码语义，靠 `id` 配对。够用，但不是 HTTP 的替代品。
- **`/api/proxy/binary` 与 `/api/pdf/*` 未纳入 apiCore**：这两组涉及流式/大二进制，与"一次请求一次响应"的 RPC 模型不匹配，本版未动。
- **无后端时协同房间不可用**：Pages 线上若留空 `VITE_BACKEND_WS_URL`，是单机演示，多人协同不存在。
- 审查报告其余阻断项（B2 沙箱可绕过、B3 PDF 无沙箱、B4 SSRF TOCTOU、B6 上传无字节上限）本版未动。
