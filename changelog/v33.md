# v33 — 回补 v30 丢失的扇出补丁，并修 PDF 上传边界与 LRU 淘汰

> 发布日期：2026-11-23

## 修复（Fixed）

- **回补 v30 的三处扇出补丁（v31/v32 交付物中已丢失）**：v31/v32 基于 v29 另起一条线，仓库 v30 的扇出修复未随之进入，导致重新回到「并发丢更新 / 计数虚高 / 重复触发」的缺陷状态。本版重新打上：
  - `src/App.tsx` 的 `emitOps` 按 `targetId + event` 归并（主调度器与 `handleRunButton` 两处）；
  - `src/core/scriptSandbox.ts` 的 `emitDownstream` 按控件去重后再计入 `count`；
  - `src/core/seedBlueprint.ts` 新增 `uniqueOutputs()`，`sendMessage` / `readChild` 同口径去重。
- **PDF 上传 15MB 边界撞车**：`server/server.ts` 的 `express.json({ limit: '20mb' })` 与 PDF 自身上限冲突——15MB 原始字节 base64 编码后恰为 20.00MB，加 JSON 包装必然超出 limit，被 express 直接 413，连 `/api/pdf/upload` 内的友好提示都到不了。已抬到 `24mb`。
- **PDF 存储淘汰不是 LRU**：`/api/pdf/:id` 读取时未刷新 Map 顺序，淘汰的始终是「最早上传」而非「最久未访问」。已在命中时 `delete` + `set` 移到队尾，恢复真正的 LRU 语义。

## 改进（Changed）

- **`countPdfPagesFromBytes` 匹配窗口 240B → 4KB**：原窗口过窄，`/Type /Pages` 与 `/Count` 间隔稍远即失配。放宽后 400B、3KB 间隔均可正确解析；函数注释同步写明「压缩流 PDF 扫不到、失败一律返回 null 由 UI 显示共 ? 页」的局限，避免后来者误以为能覆盖全部 PDF。

## 已知遗留 / 未生效项

- **压缩流 PDF 的页数统计不可用**：真实世界 PDF 多用 FlateDecode 把页对象压进 `/ObjStm`，明文正则扫不到，返回 `null`、UI 显示「共 ? 页」。要精确统计需在服务端引入成熟解析库，本版未做。
- **`/api/pdf/:id` 无鉴权**：id 为 8 字节随机（不可枚举），但链接一旦泄漏即可被任何人读取。设计上按「随机不可猜 URL」处理，未加 token。
- **`npm test` 仍未接入 `deploy-pages.yml`**：按 `AGENTS.md` 保护清单未修改仓库维护版 workflow。
- **`widgets.connect()` 仍绕过 `validateDagConnection()`**：v30 审查已记录此违规，v31/v32 未处理，本版亦未处理（超出本次合并范围）。
