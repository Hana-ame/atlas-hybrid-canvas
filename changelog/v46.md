# v46 — `/api/proxy/binary` 安全加固（防 3xx 重定向 SSRF / 流式限流防 OOM / MIME 防同源 XSS）

## 变更动机
对照此前粘贴的 16 项历史隐患清单逐条复核 v45 代码库时，在第 15 项（代理安全）复检中发现 `GET /api/proxy/binary` 存在三处真实安全缺口：
1. **3xx 重定向 SSRF 绕过**：`/api/proxy` 已配置 `redirect: 'manual'` 并拦截 3xx，但 `/api/proxy/binary` 未配置 `redirect: 'manual'`，白名单上游若返回 302 跳转到 `127.0.0.1` 或 `169.254.169.254`，Node `fetch` 会默认跟随跳转绕过 SSRF 校验。
2. **内存 OOM 风险**：`/api/proxy/binary` 先执行 `await upstream.arrayBuffer()` 全量读入内存后再比对 50MB 上限，恶意大响应可耗尽服务端内存。
3. **同源 XSS 风险**：直接透传上游 `Content-Type` 并配合 `Content-Disposition: inline`，若上游返回 `text/html` 或 `image/svg+xml` 将在同源触发脚本执行。

## 核心改动
- `server/proxySecurity.ts`：新增 `readResponseBufferWithLimit()`（先校验 `Content-Length`，再按流式分块累加字节并在超限时立刻 `AbortController.abort()` + `reader.cancel()`）与 `sanitizeBinaryProxyContentType()`（仅放行 `application/pdf` 与 `application/octet-stream`，其余强制收敛为 `application/pdf`）。
- `server/server.ts`：`GET /api/proxy/binary` 补充 `redirect: 'manual'` 与 3xx 拦截（返回 `502`），改用 `readResponseBufferWithLimit()`，并设置 `X-Content-Type-Options: nosniff` 与白名单收敛后的 `Content-Type`。
- `tests/proxySecurity.test.ts`：新增 3 项单元测试，覆盖超大 `Content-Length` 提前拒收、分块流式中途超限中断、以及 `text/html` / `image/svg+xml` MIME 净化。
