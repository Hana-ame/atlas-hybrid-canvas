# v49 历史溯源 — Blame 复核

> 复核日期：2026-11-23
> 复核对象：`changelog/v49.md` 中「历史版本 Blame 溯源（明确追责）」一节
> 结论：**该节 3 条 blame 中 2 条与仓库事实不符**，且「驳回外部 Agent 幻觉需求」一栏把协作分歧写成了单方裁决。技术方向（iframe → 逐页解包）成立，但归因需要更正

## 为什么要单独复核

`v49.md` 由交付物自带，在「核心改动」之前先放了一段「明确追责」，逐个点名 v31 / v32 / v35 用词为「偷懒」「擅自」。这类结论如果只凭印象写、不去查 changelog 和 git 历史，就会被后续读者当成既定事实继承下去。所以逐条核对。

## 逐条核对

### v31 — 描述大体成立，但措辞失当

`v49.md` 原文：
> 首次实现 PDF 控件时偷懒采用了浏览器内置 `<iframe src={iframeSrc}>` + `buildPdfIframeSrc()` 方案，直接引入了浏览器自带的多页滚动浏览视图与滚动条，并在外链带 `X-Frame-Options` / `Content-Disposition: attachment` 时报错。

核对结果：

- **技术与功能描述属实**。v31 确实首次引入 PDF 控件，实现路径确为浏览器内置渲染；`X-Frame-Options` / `Content-Disposition: attachment` 导致外链失效的机制也说得对。
- **但 `changelog/v31.md` 里 `iframe` 一词零命中**。查 `grep -n "iframe" changelog/v31.md` 无结果。也就是说 v31 的版本记录从未披露自己用的是 iframe 方案，只写了「支持直接输入 http/https PDF URL」「左右翻页与页码跳转」。这是**文档披露缺失**，比技术选型本身更值得记一笔。
- **「偷懒」不属于可核查的事实**。选 iframe 在当时是常见做法，能最快拿到多页翻页与 `#page=N`，代价是渲染不可控。用动机词替代技术判断，读者拿不到有用信息。

更正表述：v31 引入 iframe 渲染路径，功能可用但渲染行为交给浏览器，且未在 changelog 中披露该实现方式。

### v32 — 描述准确，措辞失当

`v49.md` 原文：
> 继续沿用 `<iframe src>` 浏览器内置阅读器（保留原生滚动条），并擅自增加了可反复展开的「换源」工具栏，违背一次性加载需求。

核对结果：

- **事实准确**。`changelog/v32.md` 第 8 行明确记载：「顶部 URL / 上传 / Proxy 栏在加载后自动收起，可通过底部右侧『换源』随时展开」。可反复展开的换源栏确实由 v32 引入。
- **「擅自」不成立**。v32 是独立的一个版本迭代，当时并没有「一次性加载、锁定来源」这条需求被提出过；这条需求是在 v49 才明确的。事后用新需求去追溯旧版本「违背」，是把需求演进写成违规。

更正表述：v32 在 iframe 方案上叠加了可反复展开的换源栏；该交互与 v49 确立的「一次性加载」需求冲突，故在 v49 一并移除。

### v35 — 描述不准确，需要改写

`v49.md` 原文：
> 在 `<iframe>` 之上叠加离屏休眠逻辑，继续固化了内置浏览器阅读器架构，未做 PDF 逐页解包。

核对结果：

- **v35 的主体不是 PDF**。查 `changelog/v35.md`，标题为「三环流式裁剪与方向预测预加载、分块精准脏缓存与重媒体离屏休眠」，绝对主体是视锥裁剪（Ring 0/1/2）、Chunk 脏缓存、离屏休眠三件事，PDF 只是「重媒体」这一类的代表。
- **「继续固化架构」不成立**。v35 对 iframe 只是**消费者**：把 `<iframe>` 当作需要离屏卸载的重媒体来管理（`changelog/v35.md` 第 8、17 行）。它没有任何意图去改进 PDF 渲染方式，谈不上「固化」。
- **「未做逐页解包」是评价错位**。v35 的版本目标是性能（视锥裁剪），不是 PDF 渲染保真度。要求它做逐页解包，等于拿 v49 的目标去衡量一个不相干版本。

更正表述：v35 引入三环视锥裁剪与离屏休眠，PDF 作为重媒体被纳入该机制（Ring 0 内挂载、离屏卸载）。它沿用了既有的 iframe 实现，但未改动 PDF 渲染方案本身，不属于 PDF 架构问题。

### 「驳回外部 Agent 幻觉需求」— 应改为需求澄清记录

`v49.md` 原文把两条需求差异写成「驳回幻觉」：双击缩放、保留滚动条。

核对结果：这两条在仓库 changelog 中**均无对应记录**，无法验证曾被提出过（`grep` 无命中）。也就是说，「外部 Agent 提出过这两条」这一点本身没有留痕。

更重要的是定性问题：即使确有分歧，这也是**需求理解偏差**，双方对新控件该长什么样没有对齐，不是一方凭空编造。把它写成「驳回幻觉」，是在事后单方面给协作者定性。

更正表述：v49 明确控件形态为「严格 fit 控件大小、零滚动条」，不提供双击缩放状态。此前若有过「双击放大」或「保留滚动条」的设想，均与最终需求不符，已按最终需求实现。

## 一条被两份文件都漏掉的事实

`v49.md` 把 blame 都落在 v31 / v32 / v35 这三个 changelog 文件上，但 **`src/canvas/PdfViewerBlock.tsx` 与 `src/core/pdfHelper.ts` 实际是在提交 `2b1b489`（feat(v33): 合并 PDF 阅读控件（v31-v32），回补丢失的扇出补丁）才进入仓库**：

```
$ git log --oneline --diff-filter=A -- src/canvas/PdfViewerBlock.tsx
2b1b489 feat(v33): 合并 PDF 阅读控件（v31-v32），回补丢失的扇出补丁

$ git log --oneline -S "<iframe" -- src/canvas/PdfViewerBlock.tsx
f1773d6 feat(v49): ...   # 移除
2b1b489 feat(v33): ...   # 引入
```

含义有两层：

1. **v31 / v32 当时可能并未真正落进仓库**，而是随 v33 一并合并进来的。若如此，把 blame 挂在 v31 / v32 这两个版本号上，指向的是一个未必存在的落地时点。
2. **`<iframe>` 在仓库里从 `2b1b489` 存续到 `f1773d6`**，跨 v33 → v49 共 16 个版本。这是真实的技术债存续区间，比「v31 偷懒」有用得多——它解释了为什么这个架构能活这么久：**中间没有任何一版把「PDF 该怎么渲染」当成独立问题重新审视过**。
