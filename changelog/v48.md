### 阻断 2：v46 的三处二进制代理加固，一处都没接进路由

`v46.md` 声称做了：

1. `/api/proxy/binary` 补 `redirect: 'manual'` 并拦截 3xx
2. 改用 `readResponseBufferWithLimit()` 流式限流
3. 用 `sanitizeBinaryProxyContentType()` 收敛 Content-Type + `nosniff`

实际代码：两个函数**已被 import 到 `server.ts`**（第 14、15 行），测试也写了 3 条覆盖它们，但 `/api/proxy/binary` 路由体里——

```ts
const upstream = await fetch(target.url.toString(), { method: 'GET', headers, signal: controller.signal });
const arr = Buffer.from(await upstream.arrayBuffer());   // 全量读入
if (arr.byteLength > PDF_UPLOAD_MAX_BYTES) { ... }        // 读完才比大小
res.setHeader('Content-Type', upstream.headers.get('content-type') || 'application/pdf');  // 透传
```

没有 `redirect: 'manual'`、没有流式限流、Content-Type 照原样透传。**三个漏洞一个没堵，只是把工具函数和测试写好了摆在那。**

后果：白名单上游返回 `302 Location: http://169.254.169.254/...` 时，Node `fetch` 默认跟随跳转，前面那轮 `dns.lookup` 对跳转后的地址完全无效，SSRF 成立；上游返回 `text/html` 配合 `Content-Disposition: inline`，同源执行脚本。

已按 v46 描述补进路由：`redirect: 'manual'` + 3xx → 502、`readResponseBufferWithLimit()` 流式限流、Content-Type 白名单收敛 + `X-Content-Type-Options: nosniff`。

一并修正：不把超时用的 `controller` 传给 `readResponseBufferWithLimit()`。该函数超限时会自行 `abort`，若共用同一个 controller，`fetch` 抛出的 `AbortError` 会让下面的 catch 把「超限」误报成「代理拉取失败」。

## 补充

- **`tests/proxySecurity.test.ts` +2 条**：`sanitizeBinaryProxyContentType()` 对 `text/html` / `image/svg+xml` / `application/javascript` 等一律收敛；`readResponseBufferWithLimit()` 在无 `Content-Length` 时仍按流式累加拦截超限，未超限时完整返回。原 3 条测试只测了函数本身，测不到「路由没调用它们」——这正是漏洞漏网的原因。
- **`docs/SCRIPT_API_GUIDE.md` 补 `onChange()` 章节**：v47 新增了这个 API 和「链式派生最多 3 轮」的硬上限，指南里一个字都没有。用户写「4 级派生只到第 3 级就停住」时会疑惑是不是 bug，必须写明这是 `MAX_REACTION_PASSES = 3` 的防死循环上限。

## 已确认正确

- **`onChange` 的三轮上限按设计工作**：实测 `a→b→c→d` 三级链全部完成；`a→b→c→d→e` 四级链在 `d` 停住、`e` 保持初值，与 `MAX_REACTION_PASSES = 3` 一致，不挂死不报错。
- **池化 Worker 复用不丢订阅**：同一 worker 连发两次 `click`，两次 `onChange` 均正常触发（`X:0->1`、`X:1->2`）。`runUserCode()` 每次执行前重置 `changeHandlers` 后由脚本顶层重新注册，语义正确。
- **`validateConnect` 路径不会误跑 `onChange`**：该分支在注册后立即 `postMessage` 返回，不进入 `runChangeWatchers`。
