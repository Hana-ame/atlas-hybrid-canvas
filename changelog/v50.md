# v50 — 用 Node 内建 WebSocket 房间替换 Go 服务，协同功能首次真正可用

> 发布日期：2026-11-23
> 基线：`c974817`（v49 之后）
> 起因：全仓库审查（`changelog/audit-2026-11-23-全仓库.md`）发现 B1——协同功能从未工作过

## 背景：之前的协同是"两个不相干的东西"

前端 `roomClient.ts` 用 `new WebSocket('ws://localhost:8787/ws?room=…&cid=…')`，发 `{t:'hello'|'state'|'upsert_node'|…}`。

而 `room-go/` 实际是 **PeerJS 信令客户端 + WebRTC 应答端**：

| 核对项 | 实际 |
| --- | --- |
| WS 服务端（`Upgrader`） | 全仓库零命中 |
| HTTP 路由 | 只有 `/health`、`/dump` |
| `/ws` | 不存在 |
| WebSocket 用途 | **出站** `dialer.DialContext` 连 `wss://0.peerjs.com/peerjs` |
| `hello` 处理 | 不解析，落入 `default` 静默丢弃 |

`docs/BACKEND_AND_SECURITY.md` 当时也写着「**若后续将前端接入 `room-go`**」，说明这层接入本来就从未做过。前端与 Go 服务协议、传输层、房间模型全都不匹配，**点"加入房间"必然失败**。

## 改动

### 新增 `server/roomServer.ts`（约 400 行）

Node WebSocket 房间服务，挂到 Express 同一个 `http.Server` 上，靠 `upgrade` 事件按 `/ws` 分流。

- **协议逐字对齐** `RoomWireMessage`，前端 `roomClient.ts` **零改动**
- **CRDT 裁决与 `crdt.ts` 的 `beats()` 逐行等价**：`rev` 大的赢，相同则 `cid` 字典序大的赢
- **广播在锁内只拷目标列表、解锁后再发送**（照搬原 Go 做对的地方，慢客户端不占锁）
- **新成员入房补发全量 snapshot**
- **心跳 30s**：上一轮未回 pong 的连接被 terminate，避免半开连接永久占位（原 Go 缺这层）

### 容量上限（原 Go 全部缺失）

| 项 | 上限 |
| --- | --- |
| 房间数 | 64 |
| 单房间成员 | 32 |
| 单帧 | 4MB |
| 每集合记录数 | 5000 |
| 单字符串字段 | 512KB |

### 端口与启动

`PORT` 默认值从 `3000` 改为 **`8787`**，与前端 `App.tsx` 的默认房间地址对齐。`npm run dev` 一个进程同时提供 API 与协同房间，不再需要单独拉 Go。

新增 `GET /api/room/stats` 返回在线房间数与成员数；`SIGINT`/`SIGTERM` 优雅关闭。

### 删除 `room-go/`

11 个文件、1,527 行 Go 代码全部移除。它是 PeerJS 中继，与前端协议不通，保留只会误导后来者。

### 顺带解决「设了 token 前端就 401」的死结

审查 B5 指出：`PROXY_CLIENT_TOKEN` 为空时服务端放行所有调用方，而前端**从不发送** `x-proxy-token`——设了就全 401，不设就匿名开放。

新增 `src/core/apiClient.ts` 的 `proxyHeaders()`，从 `VITE_PROXY_CLIENT_TOKEN` 读取并统一补头，三个调用点（`App.tsx` 的 `proxy_http`、`PdfViewerBlock` 的 `unpack` / `unpack-upload`）全部改走它。

## 实现过程中自查出的 4 个问题（均在提交前修掉）

1. **`state` 直接覆盖绕过 CRDT 裁决**：原实现 `replaceAll()` 清空重写，任何成员一发 `state` 就能抹掉别人的全部数据。改为逐条走 `upsert` 裁决，只有更新的记录胜出。
2. **`handleMessage` 用 `rooms.get(roomName)` 而非闭包 `room`**：房间可能因成员走空被销毁、同名新房重建，旧 socket 的消息会打进新房。改为用闭包实例 + `members.has(socket)` 守卫。
3. **最后一人离开就销毁房间状态**：数据全丢，下一个人进来是空的。改为记 `idleSince`，空闲超过 30 分钟才回收。
4. **`delete` 消息不带 rev/cid**：原先构造一个"与现有记录同 rev"的墓碑去裁决，等于同版本比较永远失败。改为直接删除，后续 upsert 用更高 rev 可正常加回。

## 测试跑通过程中修掉的两个问题

这两处是"看代码觉得对、跑起来才暴露"的典型，记在这里避免重犯。

**1. 首帧在监听器挂上之前就已经到达，被 EventEmitter 丢弃**

服务端在 `handleUpgrade` 回调里同步 `send` 全量快照。这一帧往往在客户端 `'open'` 事件之后、调用方挂 `message` 监听之前到达。`ws` 底层是 EventEmitter——**没有监听器时事件直接丢弃，不缓存**。所以「`await connect()` 之后再 `waitFor()`」的写法必然漏掉入房首帧，表现为"等待消息超时"。

这不是测试写法无关紧要的小事：它证明"入房即发快照"这条路径实际是不可靠观测的。修法是把 `Client` 包装成构造时就挂唯一监听、收到的帧进队列，`waitFor` 先查队列再等新帧。附带把 `assert.equal(flag, false)` 这类"先挂监听再 sleep"的写法统一换成 `collect(ms)`，测试不再依赖 sleep 时长。

**2. 非 `/ws` 路径的 upgrade 请求变成泄漏的半开 socket**

原实现 `if (url.pathname !== wsPath) return;`——直接 return，既不接管也不关闭。客户端永远等不到 `open` 也等不到 `error`，一直挂着。第 7 条用例因此不是断言失败，而是挂到被超时杀掉（`exitCode 143`）。

改为：若 `httpServer.listenerCount('upgrade') > 1`（确实还有别的处理器）才让位；否则明确回 `404` 并 `destroy`，让客户端立刻拿到确定结果。

## 验证

- 静态核查：`roomServer.ts` 无裸 map 并发写；广播目标列表在发送前已脱离 `members` 迭代
- 协议对齐：`WireMessage` 与 `RoomWireMessage` 逐字段核对
- 测试条数：54 → 63（新增 7 条房间服务 + 2 条 PDF 解包）
- 本地实测：63 条中 62 过，`roomServer.test.ts` **7/7 全过**
- 唯一失败项 `unpackPdfBufferToPages() … without iframe` 原因为 `spawn mutool ENOENT`——本机未装 `mutool`，属环境依赖，与本次改动无关；CI 环境下应通过
- 构建与其余测试以 CI 为准（未本地构建）

## 已知遗留

- **协同房间无鉴权**：房间名即凭据，知道就能加入。公网部署需外层反代鉴权，已在文档写明。
- **纯内存，不落盘**：进程重启状态丢失。空闲 30 分钟后也会回收。
- **`peer_joined` / `peer_left` 前端尚未消费**：消息会照常下发，但 `App.tsx` 只处理 `t === 'state'`，成员列表 UI 未接。
- 审查报告其余阻断项（B2 沙箱可绕过、B3 PDF 无沙箱、B4 SSRF TOCTOU、B6 上传无字节上限）本版未动。
